이 출처에서는 깃허브를 이용한 그룹 프로젝트의 초기 설정 단계를 **프로젝트 리더 (스크럼 마스터)**의 역할을 중심으로 상세하게 설명합니다. 초기 설정은 협업의 기반을 마련하고 효율적인 개발 워크플로우를 구축하는 데 매우 중요합니다.

**1. 리포지토리 생성 및 팀원 초대:**

*   프로젝트를 시작하는 **첫 번째 단계는 깃허브에서 새로운 리포지토리를 생성**하는 것입니다. 프로젝트 리더는 깃허브 웹사이트에서 "New" 버튼을 클릭하여 리포지토리 이름 (예: "그룹 프로젝트")을 설정하고, 공개 (Public) 또는 비공개 (Private) 설정을 선택한 후 리포지토리를 생성합니다.
*   리포지토리가 생성되면, **프로젝트 리더는 팀원들을 초대**해야 합니다. 리포지토리 페이지의 "Settings" 섹션에 있는 "Manage access" 메뉴에서 "Invite a collaborator" 버튼을 클릭하고, 팀원들의 깃허브 사용자 이름을 입력하여 초대할 수 있습니다. 초대받은 팀원들은 초대를 수락해야 리포지토리에 접근 권한을 얻게 됩니다.

**2. 초기 프로젝트 환경 설정:**

*   프로젝트 리더는 **로컬 환경에서 프로젝트의 기본적인 틀을 설정**합니다. 이는 단순히 `index.html`과 같은 초기 파일을 만드는 것부터 시작할 수 있으며, 실제 프로젝트의 기술 스택에 따라 필요한 설정 (예: 리액트 프로젝트의 초기 설정)을 포함할 수 있습니다.
*   로컬에서 초기 파일을 만든 후, **이 파일을 깃허브 리포지토리로 푸시**해야 팀원들과 공유할 수 있습니다. 이를 위해 프로젝트 리더는 터미널에서 다음 명령어를 순서대로 실행합니다:
    *   `git init`: 로컬 디렉토리를 깃 저장소로 초기화합니다.
    *   `git add .`: 모든 변경된 파일을 스테이징 영역에 추가합니다.
    *   `git commit -m "First commit"`: 첫 번째 커밋을 생성하여 변경 사항의 이력을 기록합니다.
    *   `git remote add origin [리포지토리 URL]`: 로컬 저장소를 원격 깃허브 리포지토리와 연결합니다.
    *   `git push origin master`: 로컬의 `master` 브랜치에 있는 코드를 원격 리포지토리의 `master` 브랜치로 푸시합니다. 이 시점에서 **기본 브랜치는 `master`**입니다.

**3. `develop` 브랜치 생성 및 역할 정의:**

*   프로젝트 리더는 `master` 브랜치 외에 **`develop` 브랜치를 추가로 생성**합니다. `develop` 브랜치는 `master` 브랜치의 복사본으로, **실질적인 개발 작업이 이루어지는 브랜치**입니다.
*   `develop` 브랜치를 만드는 이유는 다음과 같습니다:
    *   **안정적인 `master` 브랜치 유지:** `master` 브랜치는 최종 사용자에게 제공되는 안정적인 버전을 유지하기 위한 것입니다. 개발 과정에서 발생할 수 있는 오류나 불안정한 코드가 `master` 브랜치에 직접 반영되는 것을 방지합니다.
    *   **개발자들의 작업 공간:** 개발자들은 `develop` 브랜치를 기반으로 각자의 기능을 개발하고 테스트할 수 있습니다. 오류가 발생하거나 코드가 엉켜도 `master` 브랜치에는 영향을 주지 않습니다.
*   `develop` 브랜치는 로컬에서 다음 명령어를 사용하여 `master` 브랜치로부터 생성하고 원격 리포지토리로 푸시합니다:
    *   `git checkout -b develop`: `master` 브랜치에서 `develop` 브랜치를 생성하고 해당 브랜치로 전환합니다.
    *   `git push origin develop`: 로컬의 `develop` 브랜치를 원격 리포지토리로 푸시합니다. 이제 깃허브 리포지토리에는 `master`와 `develop` 두 개의 주요 브랜치가 존재하게 됩니다.

**4. `master` 브랜치 보호:**

*   프로젝트 리더는 **`master` 브랜치를 보호**하여 팀원들이 직접 코드를 푸시하는 것을 방지해야 합니다. 이는 `master` 브랜치의 안정성을 유지하는 데 필수적인 조치입니다.
*   깃허브 리포지토리 설정에서 "Branches" 섹션으로 이동하여 `master` 브랜치 보호 규칙을 설정할 수 있습니다. 주요 보호 규칙은 다음과 같습니다:
    *   **푸시(Push) 금지:** 팀원들이 `master` 브랜치에 직접적으로 `git push` 명령어를 사용하는 것을 막습니다.
    *   **풀 리퀘스트(Pull Request) 필수:** `master` 브랜치로 코드를 병합하기 위해서는 반드시 풀 리퀘스트를 거치도록 강제합니다. 이를 통해 코드 리뷰 과정을 통해 코드의 품질을 관리하고 잠재적인 문제를 사전에 발견할 수 있습니다.

이러한 초기 설정 과정을 통해 깃허브 그룹 프로젝트는 체계적인 브랜치 전략을 갖추고, 코드의 안정성을 유지하며, 효율적인 협업 환경을 구축할 수 있습니다. 이후의 개발 작업은 주로 `develop` 브랜치에서 이루어지며, 각 기능 개발은 `develop` 브랜치에서 파생된 개별 피처 브랜치에서 진행됩니다. 완성된 기능은 풀 리퀘스트를 통해 `develop` 브랜치로 병합되고, 충분한 테스트와 검토를 거친 `develop` 브랜치의 코드는 최종적으로 `master` 브랜치로 병합되어 배포됩니다.
